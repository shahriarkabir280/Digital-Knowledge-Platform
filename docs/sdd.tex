\section{System Overview}

\subsection*{Problem Summary}
\begin{itemize}
    \item Existing institutional knowledge systems are fragmented across archive, repository, library, and project showcase modules.
    \item Fragmentation reduces discoverability, research visibility, and operational efficiency for students, faculty, and staff.
    \item Current workflows lack integrated collaboration, bilingual intelligence, analytics, and preservation-aware management.
\end{itemize}

\subsection*{Target Users}
\begin{itemize}
    \item \textbf{Students (Member role):} Access learning resources, research papers, project showcases, and collaboration tools.
    \item \textbf{Researchers/Faculty (Contributor role):} Submit outputs, discover related work, and analyze citation and impact trends.
    \item \textbf{Librarians (Staff role):} Manage catalog and circulation workflows with reporting, imports, and barcode/QR operations.
    \item \textbf{Archive Managers (Staff role):} Preserve institutional documents with metadata, integrity checks, and migration planning.
    \item \textbf{Administrators (Administrator role):} Govern users, permissions, analytics, compliance, and overall system operations.
    \item \textbf{General Public (Guest role):} Search and view publicly published institutional knowledge resources.
\end{itemize}

\subsection*{Project Goals}
\begin{itemize}
    \item \textbf{Archive Upload \& Metadata Editor:} Develop a robust ingestion system for multi-format media with a rich metadata editor, supporting bulk uploads and automated field mapping for efficient archival.
    \item \textbf{Public Search/Browse \& Media Viewer:} Implement an intuitive, bilingual (Bangla-English) discovery interface with an integrated high-performance viewer for PDFs, images, and streaming audio/video content.
    \item \textbf{Research \& Showcase Pages:} Create specialized, high-visibility portals for institutional research outputs, laboratory portfolios, and academic project showcases to highlight innovation and excellence.
    \item \textbf{Public Catalog Portal:} Deliver a centralized, user-friendly digital library catalog with advanced filtering, allowing users to browse physical and digital collections in real-time.
    \item \textbf{Member Borrowing Workflow:} Automate the complete circulation lifecycle, including digital hold requests, wishlist management, personal history tracking, and automated due-date notifications.
    \item \textbf{Librarian Operations Dashboard \& Reports:} Provide a comprehensive administrative command center for CRUD operations, inventory management, and the generation of detailed analytics and usage reports.
\end{itemize}

\subsection*{Out of Scope}
\begin{itemize}
    \item Course/LMS delivery and grade management are excluded from this platform scope.
    \item Native mobile apps are excluded for Phase 1, with responsive web as the delivery mode.
    \item Building a video conferencing platform or full communication suite is outside scope.
    \item Payment gateway integration and hardware procurement are excluded from the software MVP.
\end{itemize}

\section{Architecture Design}
\subsection{High-Level Architecture}
\textbf{Main components/services:}
\begin{itemize}
    \item \textbf{Auth Service}: Handles login, password reset, session/token lifecycle, and role lookup.
    \item \textbf{Repository Service}: Manages research/project submissions, metadata, versions, and review state.
    \item \textbf{Library Service}: Manages catalog CRUD, circulation workflows, fines, and hold requests.
    \item \textbf{OCR/AI Worker}: Runs asynchronous OCR, summarization, recommendation, and plagiarism jobs.
    \item \textbf{Search Service}: Provides bilingual indexed search and filtering for all discoverable content.
    \item \textbf{Notification Service}: Sends event-driven emails for review updates, due reminders, and alerts.
    \item \textbf{Analytics Service}: Aggregates usage, research trends, and operational KPIs for dashboards.
    \item \textbf{Data Layer}: PostgreSQL (transactional), Redis (cache), Queue broker, and object storage.
\end{itemize}

\textbf{Data Flow Summary:}
\begin{itemize}
\item \textbf{User Requests} from the Web UI pass through an \textbf{API Gateway} to be \textbf{authenticated} and routed to the correct \textbf{domain services}.
\item \textbf{Domain services} then \textbf{save transactional data} into the \textbf{database} and \textbf{store files} in \textbf{object storage}.
\item Heavy \textbf{AI or OCR tasks} are sent to a \textbf{queue} to be processed \textbf{asynchronously} by separate \textbf{worker nodes}.
\item Once complete, the \textbf{workers update search indexes} and \textbf{trigger notifications} or \textbf{analytics events}.
\item For \textbf{fast performance}, \textbf{search requests} and \textbf{dashboards} read directly from these \textbf{optimized data stores}.
\end{itemize}

\subsection*{Key Relationships}
\begin{itemize}
    \item One User uploads many Documents; each Document belongs to exactly one uploader.
    \item One Document has exactly one Metadata record (one-to-one cardinality).
    \item One Document has many Annotations; one User can create many Annotations.
    \item One CatalogItem has many Loan records over time; active loan count is constrained by availability.
    \item ResearchPaper has many-to-many self-citations through Citation edges.
    \item One Lab has many ResearchPapers; each ResearchPaper belongs to one Lab.
    \item One Document can have many Preservation records for periodic integrity and migration tracking.
\end{itemize}

\subsection*{Constraints and Validation Rules}
\begin{itemize}
    \item User email must be unique and conform to institutional email format policy.
    \item Document file\_size must be $\leq$ 500MB and format must be in the allowed media list.
    \item Document state must be one of: \texttt{draft}, \texttt{review}, \texttt{published}, \texttt{archived}.
    \item access\_tier must be one of: \texttt{public}, \texttt{member}, \texttt{staff}, \texttt{restricted}.
    \item Barcode values in CatalogItem must be unique across the catalog.
    \item For Loan, \texttt{due\_date} must be greater than \texttt{checkout\_date} and required while loan is active.
    \item Annotation visibility must follow role/access policy before rendering to other users.
    \item Audit-sensitive operations must write immutable log entries with timestamp and actor reference.
\end{itemize}

\subsection*{Data Lifecycle and Retention/Deletion Rules}
\begin{itemize}
    \item Document lifecycle: \texttt{draft} $\rightarrow$ \texttt{review} $\rightarrow$ \texttt{published} $\rightarrow$ \texttt{archived}.
    \item Each document update creates a new version; previous versions remain restorable for authorized staff.
    \item OCR/AI outputs are persisted as derived metadata and can be recalculated when models are updated.
    \item Backup lifecycle follows daily incremental and weekly full snapshot policy.
    \item Activity/audit logs are retained for 1 year to satisfy operational traceability requirements.
    \item GDPR-style deletion requests remove personal profile/content ownership data where applicable.
    \item When deletion is requested, audit logs are retained but user identifiers are anonymized (hashed).
    \item Archived and preservation-marked records remain queryable to staff per access tier and policy.
\end{itemize}

\section{Core Flow Design}
\subsection*{Flow 1: Research Submission + Plagiarism + Summary + Review}
\textbf{Trigger:} A Contributor/Researcher starts a new paper submission from the repository module.

\textbf{Steps:}
\begin{enumerate}
    \item User opens \texttt{Research Repository > Submit Paper} and uploads PDF/DOCX.
    \item System validates file type/size, performs malware scan, and stores the file in object storage.
    \item System extracts metadata (title, authors, abstract, keywords) and pre-fills submission form.
    \item User reviews/edits metadata, selects lab/department, access tier, and submits for processing.
    \item System enqueues plagiarism and AI summarization jobs in queue broker.
    \item Worker executes plagiarism check and generates summary/key findings asynchronously.
    \item System updates submission record with score, summary, and processing timestamps.
    \item User reviews generated outputs and either accepts or edits summary before final submit.
    \item System assigns submission ID, sets state to \texttt{review}, and notifies assigned reviewers.
\end{enumerate}

\textbf{Success outcome:}
\begin{itemize}
    \item Submission is stored with searchable metadata, review state, and versioned artifacts.
    \item Plagiarism report and summary are attached to the submission record.
    \item Reviewer notification is sent and audit log entry is created.
\end{itemize}

\textbf{Failure/edge cases:}
\begin{itemize}
    \item Invalid file format or size limit exceeded $\rightarrow$ reject upload with actionable validation message.
    \item Plagiarism service timeout $\rightarrow$ keep submission in pending-processing state and retry from queue.
    \item Plagiarism score above policy threshold $\rightarrow$ show warning, require user confirmation/manual review path.
    \item Summary generation fails $\rightarrow$ allow manual summary entry; record failure event in logs.
    \item Reviewer assignment unavailable $\rightarrow$ route to staff review pool and notify administrator.
\end{itemize}

\subsection*{Flow 2: Library Checkout/Return + Due Tracking/Notification}
\textbf{Trigger:} Librarian scans member ID and item barcode/QR at circulation desk.

\textbf{Steps:}
\begin{enumerate}
    \item Librarian authenticates and opens circulation interface.
    \item System reads member profile, role/status, loan limits, fines, and active holds.
    \item Librarian scans item code; system fetches item availability and policy constraints.
    \item On checkout, system creates \texttt{Loan} record, computes due date, updates item status to \texttt{checked\_out}.
    \item Notification service sends checkout confirmation with due date and renewal rules.
    \item Scheduler evaluates due-tracking jobs daily and triggers reminder/overdue notifications.
    \item On return scan, system closes loan, computes overdue fine (if any), and sets item to \texttt{available}.
    \item System records circulation/audit events and refreshes member history/reporting aggregates.
\end{enumerate}

\textbf{Success outcome:}
\begin{itemize}
    \item Loan lifecycle is accurately recorded from checkout to return.
    \item Member receives due/overdue notifications at configured schedule.
    \item Item status, fines, and borrowing history remain consistent across modules.
\end{itemize}

\textbf{Failure/edge cases:}
\begin{itemize}
    \item Member exceeds loan limit or has blocking fines $\rightarrow$ block checkout and show override policy.
    \item Item already checked out $\rightarrow$ prevent checkout and offer hold placement workflow.
    \item Notification delivery failure $\rightarrow$ retry with backoff; keep delivery log and alert staff if exhausted.
    \item Return scan mismatch or unreadable code $\rightarrow$ fallback to manual lookup with dual confirmation.
    \item Due-tracking job delay $\rightarrow$ run catch-up processing and mark delayed notifications in ops log.
\end{itemize}

\subsection*{Flow 3: Fine Calculation + Payment/Settlement Recording}
\textbf{Trigger:} Overdue return or damaged item event is detected during circulation processing.

\textbf{Steps:}
\begin{enumerate}
    \item Librarian opens the active loan record from circulation history.
    \item System computes overdue duration from \texttt{due\_date} and return timestamp, then applies configured fine rules.
    \item If damage is reported, staff selects damage category and system adds policy-based damage charge.
    \item System generates a provisional settlement summary (overdue fine + damage charge + waivers/discounts if authorized).
    \item Librarian confirms settlement and records payment method (cash, card, or institutional wallet/manual ledger).
    \item System marks settlement status as \texttt{paid}, \texttt{partially\_paid}, or \texttt{waived} with approver metadata.
    \item Member account balance, borrowing eligibility flags, and audit logs are updated.
    \item Receipt/confirmation is issued and optional notification is sent to the member.
\end{enumerate}

\textbf{Success outcome:}
\begin{itemize}
    \item Fine and settlement records are stored with traceable calculation inputs and approval metadata.
    \item Member liability state and circulation eligibility are consistent across account and loan modules.
    \item Audit trail captures settlement actor, timestamp, amount breakdown, and status transition.
\end{itemize}

\textbf{Failure/edge cases:}
\begin{itemize}
    \item Loan record missing/closed inconsistency $\rightarrow$ block settlement, require staff reconciliation path.
    \item Policy configuration unavailable $\rightarrow$ fallback to default fine rule and flag for admin review.
    \item Partial payment recorded $\rightarrow$ keep residual balance, mark account as restricted by policy threshold.
    \item Unauthorized waiver attempt $\rightarrow$ reject action and require elevated approver role.
    \item Receipt generation or notification failure $\rightarrow$ retain settlement commit and enqueue retry event.
\end{itemize}

\subsection*{Flow 4: Advanced Search + Faceted Filtering + Access-Tier Enforcement}
\textbf{Trigger:} User submits a multilingual search query with optional filters/facets.

\textbf{Steps:}
\begin{enumerate}
    \item User enters Bangla/English keyword query and selects optional filters (type, year, lab, author, access tier).
    \item Search service normalizes text (tokenization/stemming/synonym expansion) and builds ranked query plan.
    \item System resolves user role/session claims and derives allowed visibility scope from RBAC and access tiers.
    \item Search engine executes full-text and facet aggregation query across indexed metadata/OCR fields.
    \item Result set is post-filtered to enforce permission rules before rendering snippets and file actions.
    \item System returns ranked results with facet counts, highlighted matches, and sort options.
    \item User applies additional filters or opens a result; access-controlled content view is served accordingly.
    \item Query and click events are logged for analytics and relevance tuning.
\end{enumerate}

\textbf{Success outcome:}
\begin{itemize}
    \item User receives relevant multilingual results with fast response and accurate facet counts.
    \item Restricted content is never exposed beyond role and access-tier policy.
    \item Search telemetry is captured for dashboard metrics and ranking improvements.
\end{itemize}

\textbf{Failure/edge cases:}
\begin{itemize}
    \item Empty or invalid query $\rightarrow$ return validation prompt and suggestion terms.
    \item Search index lag/staleness $\rightarrow$ show last-indexed timestamp and allow retry/refresh path.
    \item Unauthorized direct resource open $\rightarrow$ deny with access message and log security event.
    \item High-latency query under heavy load $\rightarrow$ return partial results with degraded-mode notice.
    \item Mixed-language tokenization miss $\rightarrow$ provide fallback fuzzy match and related-term suggestions.
\end{itemize}

\section{Security and Access Design}
\subsection*{Authentication Approach}
\begin{itemize}
    \item Email/password authentication with institutional account policy and optional MFA for staff/admin roles.
    \item Session/JWT tokens with secure storage, inactivity timeout at 30 minutes, and warning at 2 minutes before expiry.
    \item Password reset uses single-use, time-bound tokens and audited recovery events.
\end{itemize}

\subsection*{Authorization Model (Roles/Permissions)}
\begin{itemize}
    \item RBAC is enforced at both API and data access layers for Guest, Member, Contributor, Staff, Admin, Reviewer.
    \item Access tiers (public/member/staff/restricted) are checked before file, metadata, and annotation visibility.
    \item High-risk actions (state transitions, deletion, bulk import, policy updates) require elevated role checks.
\end{itemize}

\subsection*{Sensitive Data Handling}
\begin{itemize}
    \item TLS 1.3 for data in transit and encrypted storage for sensitive records at rest.
    \item Uploaded files validated by MIME/type/size checks and malware scanning before persistence.
    \item PII minimization applied in analytics outputs; only aggregated/anonymized data exposed in dashboards.
    \item User deletion requests remove personal profile-linked data while preserving policy-required records.
\end{itemize}

\subsection*{Audit/Logging Plan (Contradiction-Safe)}
\begin{itemize}
    \item Log all sensitive operations with timestamp, actor role, action, and target object reference.
    \item Retain audit logs for 1 year for traceability, incident response, and compliance review.
    \item On deletion requests, direct identifiers in logs are anonymized (hashed) rather than fully erased.
    \item Maintain immutable append-only log store with access limited to authorized security/staff roles.
\end{itemize}

\section{Testing Plan (Design Level)}
\subsection*{Unit Testing Targets}
\begin{itemize}
    \item \textbf{Auth Service:} credential validation, token issue/refresh/revoke, role claim parsing, timeout warning logic.
    \item \textbf{Repository Service:} metadata validation, lifecycle state transitions, version increment logic, access-tier checks.
    \item \textbf{Library Service:} checkout/return rules, due-date calculator, renewal limits, fine computation, hold queue behavior.
    \item \textbf{OCR/AI Worker:} job payload validation, retry/backoff decisions, result parser, fallback to manual summary path.
    \item \textbf{Search Service:} query normalization, bilingual tokenization helpers, ranking filter composition.
    \item \textbf{Notification Service:} template rendering, recipient policy checks, retry scheduling, dead-letter routing rules.
    \item \textbf{Analytics Service:} event aggregation functions, metric calculators, anonymization utilities.
    \item \textbf{Data Layer Adapters:} repository methods, cache key TTL behavior, object-storage URI signing helpers.
\end{itemize}

\subsection*{Integration Testing Targets}
\begin{itemize}
    \item Auth + RBAC + API gateway: protected endpoint access by role and tier-based content visibility.
    \item Repository + Queue + Worker: submission event creates jobs; worker updates status/artifacts in repository.
    \item Library + Notification: checkout/return updates trigger due reminders and overdue notification schedule.
    \item Repository + Search: metadata/OCR outputs are indexed and become queryable with expected filters.
    \item Worker + Storage + DB: OCR/summary artifacts persisted and linked to correct document versions.
    \item Compliance integration: deletion request pipeline anonymizes audit log identifiers while preserving 1-year retention.
    \item Observability integration: processing failures produce logs, metrics, and alert events with correlation IDs.
\end{itemize}

\subsection*{E2E Testing Targets}
\begin{itemize}
    \item \textbf{E2E-01 Submission Journey:} contributor uploads paper, receives plagiarism/summary outputs, submits to review.
    \item \textbf{E2E-02 Review Journey:} reviewer receives assignment, posts feedback, and changes recommendation state.
    \item \textbf{E2E-03 Circulation Journey:} librarian checkout/return flow including due tracking and reminder notifications.
    \item \textbf{E2E-04 Discovery Journey:} user performs bilingual search and opens accessible content by role/tier.
    \item \textbf{E2E-05 Compliance Journey:} user deletion request processed with retained but anonymized audit traces.
    \item \textbf{E2E-06 Session Journey:} inactivity timeout and 2-minute warning behavior validated end-to-end.
\end{itemize}

\subsection*{Known Hard-to-Test Areas (AI/OCR and Async Queue)}
\begin{itemize}
    \item Non-deterministic AI outputs can cause flaky assertions; use threshold-based checks and golden reference sets.
    \item OCR quality varies by scan quality/font; validate with benchmark datasets and CER distribution, not single samples.
    \item Queue timing/race conditions (duplicate jobs, out-of-order completion) require deterministic test harness and idempotency checks.
    \item Retry/dead-letter behavior is time-dependent; use controllable clocks or shortened test retry windows.
    \item External optional APIs (Phase 2) may be unavailable in CI; test via mocks/contracts and run limited staging smoke tests.
\end{itemize}

\subsection*{Test Environment and Exit Signals}
\begin{itemize}
    \item Unit tests run on every merge request; integration suite runs on main branch and release candidates.
    \item E2E suite runs against staging with production-like queue/storage configuration.
    \item Exit criteria: critical E2E paths pass, no unresolved high-severity defects, and benchmark thresholds met for OCR/summary quality.
\end{itemize}
